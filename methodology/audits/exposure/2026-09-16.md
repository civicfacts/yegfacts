## 2. Why PII falls by five

The six warnings the 2026-09-15 record accepted are gone, and one new one takes
their place.

**Gone: six documentation addresses in the deleted files.** Two were in
`tests/fixtures/request-capture/req-0003.json` and `req-0005.json`, the two main
turns of the sanitized capture fixture; four were in `tests/request-proof.test.ts`.
All six were RFC 2606 documentation addresses standing in for the founder's
account address, which the vendor's own reminder block puts in every request.
The fixture existed because the v1.29 check compared every byte of a request
against a pinned description, and only a real capture could satisfy it. The v1.30
check asks whether this machine's private text appears in the request, which any
request body can answer, so the fixture has no job left and is deleted rather than
kept.

**New: one documentation address in `tests/stub-request-poster.mjs:103`. ACCEPTED.**
The stub that posts through the recording proxy now writes its own request bodies
instead of replaying the fixture, and one of them is the account-email reminder
block a real request carries. The address in it is `user@example.com`, which
cannot belong to anyone. The scanner has no way to know that and should not be
taught to guess, so it stays a warning and the disposition is recorded here rather
than by loosening the rule.

## 3. Deliberate non-exposure in the same batch

One of the three items recorded on 2026-09-15 no longer applies, two carry over,
and one is new.

- **The vendor default system prompt is no longer handled at all**, because it is
  no longer pinned, hashed or referenced. v1.29 pinned it by SHA-256 and carried a
  stand-in for it in the fixture. v1.30 has no pin and no stand-in, and the vendor's
  text was never in this repository under either.
- **The raw captures** still stay outside the repository. They hold the founder's
  account address, account UUID and device id, and nothing derived from them is
  committed any more.
- **The private text the new check reads.** This is the new one, and it is the
  reason the check is written the way it is. The denylist is built from the
  operator's own `CLAUDE.md` and `AGENTS.md` files, every project memory file, the
  home directory path, the repository path and the attempt's canary token. None of
  it is written anywhere. A failure is reported as a source name and a line number,
  source names are symbolic (`$HOME/...`, `<repo>/...`) rather than real paths, and
  the public run row carries those names, whether each source existed and how many
  lines of it were searched for. A report that quoted a leaking line to prove a leak
  would republish the private text into the record defending it.
- **The CLI executable path and its hash.** The launcher retains both privately in
  the attempt metadata; `scripts/panel/attempt-record.ts` copies neither into the
  public manifest row, because one names a path on the founder's machine and the
  other is a fingerprint of a file nobody else can fetch. Which build ran is public
  as `cli_version`.
