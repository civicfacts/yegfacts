## Fit

v1.28 refused every seat on a precise ground: an empty plugin inventory shows
what was not loaded and cannot show what was sent. A capture at the gateway the
CLI is configured to use is the first artifact that speaks to that question
rather than around it. The pins sit in one exported table with a test on their
values, an unpinned version stops before a package is sent, the capture is
retained privately with only hashes and counts published, and admission is a
narrower gate than the check passing. That is the shape D-0036 asked for, and
the public wording keeps the limits as limits.

## Benefits

An unrecognised request shape fails rather than shrugs, which makes this
evidence instead of a filter. Separating "every check passed" from "admitted for
research" is the right seam: a capture against a stub upstream, or a substitute
pin table, can never be admitted, and the reason lands on the record. Disclosing
the account email and working directory is correct; stripping them would rewrite
the request and destroy the artifact offered as proof.

## Risks and disagreements

The check does not examine tool result content, and the public wording claims it
does. The scan for added instruction text reads a `text` field that a
tool_result does not have; its payload sits in `content`. The v1.29 highlight says later messages carry "no
instruction text added between turns". The checker does not establish that, and
a reminder appended to a tool result is the likeliest place in this CLI family
for one to appear. Fix the check or drop the clause.

The boundary is the client edge, not the model. Every main turn is account
linked by device id, account id and billing header. A capture shows the local
CLI added nothing beyond the pinned set; it cannot exclude context attached on
the vendor side for that account. The public paragraph answers a different
objection, that nothing else on the machine is watched. State this one too.

The working directory shown to the reviewer sits under a path naming the
project, and with the account email beside it the reviewer is told whose work it
is reviewing. Not an instruction, but for a framing check independence means not
knowing the commissioning party. Run attempts from a neutrally named directory,
a rename and not a request rewrite.

On the session naming request my concern is accounting, not leakage: the package
reaches the vendor twice per attempt, once for research and once to be named.
The changelog says so; the methodology page does not, and a reader counting
requests finds a second copy of the brief unexplained.

Publishing v1.29 with one seat is honest as written, framed as evidence about an
execution path and not a panel restart. It must never become grounds for a one
seat finding.

Both follow ups help; neither changes my view. Running the pinned installed
build closes a real hole, since the version string selecting the pins came from
the same shim and could otherwise describe a build that did not run.

## Recommendation

Conditional approval, on four conditions. Either check tool result content for
added instruction text or remove the claim that later turns carry none. Add the
vendor side limit to the public paragraph, beside the machine side one. Say on
the methodology page that the package is sent twice per attempt. Move research
attempts to a working directory that does not name the project, or disclose that
it does.

## What would change my mind

Evidence that some request path does not honour the configured gateway, making
the capture incomplete rather than limited. A live capture showing host text
inside tool results, with the claim left standing, turns the first condition
into a reject. Any rewording that calls this isolation is a reject.
